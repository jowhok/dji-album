# DJI 相册（dji-album）代码评审

- 评审时间：2026-11-26
- 评审范围：`D:\AI_WS\dji-album` 全部源码（main / preload / renderer / shared，约 30 个文件）、`scripts/` 测试与回归脚本、`package.json` 打包配置；上层目录 `DJI_APP_Requirement.txt`、`DJI相册-开发计划.md`、`overview.md`
- 评审方式：逐文件通读 + 关键路径推演 + `npm run typecheck` 实跑（通过）；未改动任何代码、未运行会碰 NAS 的操作

---

## 结论

功能完成度和"能跑起来"的自证质量明显高于同类个人项目：Range 流式代理、HEVC 直接解码、软删除/彻底删除的两段式设计、主进程白名单、纯函数抽离单测都做得扎实，`overview.md` 也是少见的老实交付日志（明确写了"彻底删除未在真实 NAS 上验证过"）。

但存在 **4 个必须修的正确性/资源问题**（其中 2 个会直接造成数据或界面不一致），以及若干与开发计划承诺不符的缺口。主要风险不在功能实现，而在 **数据一致性、并发控制、可维护性（无版本控制、测试不可复现）**。

## 一、必须修（P0）

### 1.1 重新扫描只清 `files`，不带走 `favorites` / `trash` → 计数虚高、回收站记录永远删不掉

`src/main/scanner.ts:100-105` 的失效条目清理只 `DELETE FROM files`：

```ts
const stale = (db.prepare('SELECT path FROM files').all() as {path:string}[])
  .filter((r) => !seen.has(r.path))
db.transaction(() => stale.forEach((r) => del.run(r.path)))()
```

后果链：

- `src/main/ipc.ts:108-109` 的 `app:info` 用 `COUNT(*) FROM favorites` / `FROM trash`，不 JOIN 索引 → **设置页显示的收藏/回收站数量与两个页面实际条数不一致**。
- `src/main/ipc.ts:250-258` `trash:list` 是 `JOIN files`，孤儿回收站记录在界面上看不见 → 用户既无法"恢复"，也无法"彻底删除"。
- `src/main/ipc.ts:271-290` 的 `purgePreview` 走 `buildPurgePlan`（`purge.ts:32-37` 要求 `JOIN trash` 命中，同时 `SELECT ... FROM files`），对孤儿路径返回空 → 弹窗里只会出现"有 N 项未通过安全校验"，用户完全无法理解。
- `favorites` 是软链接语义，NAS 上文件被删/改名后重新扫描，收藏丢失且没有提示。

建议：失效清理改成一个事务里 `DELETE files / favorites / trash`（或先做 `NOT EXISTS` 反连接），并顺带删掉对应缩略图；`app:info` 的收藏/回收站计数改为 `JOIN files` 口径。

### 1.2 `settings:save` 先落盘再测连接 → 报"保存失败"但配置已经生效

`src/main/ipc.ts:76-80`：`saveSettings()` 内部先 `writeFileSync(... configured:true)`（`settings.ts:44-48`），然后才 `testConnection()`；渲染层 `SettingsView.tsx:111-114` 把 `!r.ok` 显示成"保存失败"。实际状态是 **配置已写入并标记 configured，只是连不通**。下次启动会跳过引导页直接进主界面，然后全站空态。

建议：先 `testConnection`，通过后再写盘；或返回值区分 `{saved:true, connected:false}`，界面文案改成"已保存，但当前连不上 NAS"。

### 1.3 缩略图 / 元数据生成没有主进程互斥，首次启动两条队列同时打 NAS

- `src/main/ipc.ts:158-166`、`168-175` 直接把 `generateAllThumbs()` / `generateAllMetadata()` 暴露成可重复进入的 IPC。
- `Timeline.tsx:239-251` 在 rows 有缺缩略图时**自动**触发一次；`SettingsView.tsx:144-160` 又能手动触发；两个页面（时光轴 / 设置）之间不共享 `thumbBusy`。
- 首次启动时 `Timeline` 还同时触发缩略图（CONCURRENCY 3）和元数据（CONCURRENCY 3）→ **6 个 ffmpeg 同时从 SMB 读 4K 原片**，WiFi 上是实打实的带宽争抢。
- 两路 `generateAllThumbs` 会同时对同一路径 `-y` 写同一个输出文件（`thumbnails.ts:64-99`），可能产出半张图（`valid()` 只判大小 >500 字节，拦不住截断）。

建议：主进程维护 `inflightThumb` / `inflightMeta` Promise 单飞；再把缩略图与元数据共用一个任务队列（总并发 2~3），先缩略图后元数据。

### 1.4 没有单实例锁

`src/main/index.ts:55` 起直接 `whenReady → initDb → startMediaServer → createWindow`，没有 `app.requestSingleInstanceLock()`。安装版和便携版共用同一个 `userData`（`%APPDATA%/dji-album`），同时打开会出现：两个媒体服务、两个 DB 连接（WAL 能容忍读，但写入与缩略图文件会互相覆盖）、双份 ffmpeg 任务。个人自用容易踩到。

## 二、应修（P1，行为与体验）

1. **收藏页取消收藏会把播放器直接关掉**：`Timeline.tsx:328` 的 `playingItem` 由 `rows` 派生，收藏页里点"取消收藏"→ `load()` 后该条从 rows 消失 → `playingItem` 变 `null` → `Player` 卸载。用户正在看的画面会突然消失。建议 `playing` 状态独立于列表，或在 `scope==='favorites'` 时保留当前项直到关闭。
2. **缩略图加载失败是"粘性"的**：`Timeline.tsx:47,143,459` 的 `broken` Set 只增不减，重新生成缩略图后（`generateThumbs` → `load()`）卡片仍停在"缩略图失效"，必须切页面/重启才恢复。同时 `media-server.ts:123-127` 给 `/thumb/` 设了 `public, max-age=86400`，重建后同名文件浏览器仍用旧缓存。建议 `load()` 时清空 `broken`，或在 URL 上加 `?v=<mtime>` 并降为短缓存。
3. **生成过程中疯狂整页重载**：`Timeline.tsx:210-217` 每 20 张就 `loadRef.current()` 一次，而 `load` 里 `setVisible(FIRST_BATCH)`（`Timeline.tsx:167`）→ 411 张图会触发约 20 次全量 SQL + 全量重渲染，还会把用户"加载更多"到的页数重置回 500。
4. **下载进度每条 chunk 发一次 IPC**：`ipc.ts:323-325` 对 4 GB 视频约 6 万条消息。建议按 100 ms 或 1% 节流。
5. **照片预览直接放 8K 原图**：`Player.tsx:309` 用 `/media/` 拉原 JPG，实测 7680×4320。需求文档里明确写了"照片可以压缩作预览"，目前没做。建议 sharp 生成 1920~2560px 预览缓存（与缩略图同一套 LRU），播放器只放大图。
6. **`taken_at` 取的是文件 mtime**（`scanner.ts:64,74,90`），不是真实拍摄时间。DJI 上传后 mtime 常等于上传时间，"按拍摄时间排序"的语义会漂。MP4 可用 `ffmpeg` 的 `creation_time`、JPG 可用 EXIF `DateTimeOriginal`（sharp 已能读 `exif`）。
7. **瀑布流缺宽高，加载时抖**：DB 里已有 `width/height`（`metadata.ts`），但 `Timeline` 没用，全部靠 `<img>` 加载完撑开高度。用 `aspect-ratio` 预占位可显著减少跳动，也能让虚拟化更好做。
8. **扫描范围偏窄**：`scanner.ts:21-24` 只认一层、仅 `^\d{8}$` 的目录；`.lrf/.mp4` 之外的照片只认 `.jpg/.jpeg`。DJI Pocket 若产生子目录、`PANORAMA`/`DNG`/`.png` 会静默漏掉。
9. **下载过滤器对照片不对**：`ipc.ts:307-314` 恒用"视频文件 mp4"过滤器，照片另存为时默认扩展名与过滤器冲突。
10. **F11 状态可能滞后**：`ipc.ts:50-58` 的 `setFullScreen` 是异步的，函数里立刻 `win.isFullScreen()` 返回旧值，`App` 拿它 setState，靠事件广播再更正，中间会闪一下。
11. **`trimCache` 按 mtime 淘汰**（`cache.ts:29`），常看的老缩略图会被先删；按访问时间或命中计数更合理（当前量级 8 MB / 512 MB 上限，影响很小）。

## 三、安全加固（P2）

- `src/main/index.ts:29-34`：`sandbox: false`。preload 只用了 `contextBridge` + `ipcRenderer`，可以直接开 `sandbox: true`。
- 没有 `webContents.setWindowOpenHandler(() => ({ action: 'deny' }))` 和 `will-navigate` 白名单；页面本身不加载远程内容，但缺这层兜底。
- `src/renderer/index.html:6-9` CSP 缺 `connect-src` / `object-src 'none'` / `base-uri 'none'` / `frame-ancestors`。目前够用，属纵深防御。
- 媒体 token 是 `sha1(绝对路径)`（`media-server.ts:17`），确定且永久有效；虽只监听 127.0.0.1，建议加进程内随机 salt + 有限条目上限。
- `purge.ts:110` 用 `item.thumb` 直接 `win32.join(getThumbsDir(), item.thumb)`，建议加 `basename` + 40hex 校验，避免 DB 被改写时越界删缓存。
- `ipcMain.handle` 都注册在 `registerIpc(win)`（`ipc.ts:38`，由 `createWindow` 调用）。窗口重建（`app.on('activate')`）会二次注册同名 handler 抛错；建议 handler 只注册一次、用 `event.sender` 取代闭包里的 `win`，并对 `win.webContents.send` 加 `isDestroyed()` 判断。
- `settings.ts:9-14` 把真实 NAS 主机名/共享名/账号写进源码默认值。自用无妨，一旦分享或开源就是信息泄露。
- 便携版数据仍在 `%APPDATA%`（未用 `PORTABLE_EXECUTABLE_DIR`），"免安装"并不"随身"。如有需要可切换数据目录。

## 四、可维护性（最需要正视的一类问题）

1. **没有版本控制**：项目 30 个源文件、20+ 脚本、三个版本打包产物，本机连 `git` 都没装。任何一次改坏都无法回滚，也无法 diff 出"这轮改了什么"。这是当前最大的工程风险，优先级应高于任何功能修复。
2. **单测不可复现**：`scripts/test-*.mjs` 依赖 `.tmp/test-*.cjs`（esbuild 产物），而 `.tmp` 在 `.gitignore` 里，`package.json` 里**没有任何脚本能重新生成它**。换台机器 / 重装后单测直接跑不起来。建议加 `scripts/build-tests.mjs`（esbuild 打包 `scripts/test-entry-*.ts`）并接到 `npm test`。
3. **`package.json` 没有 `test` 入口**：只有 `check:all`（CDP E2E，需手动带 `--remote-debugging-port` 启动应用 + 真实 NAS）。E2E 质量不错（真实 `Input.dispatchMouseEvent`、能发现"自动化绿、真人点不了"），但它不在门禁里，也没有 CI。
4. **类型手工同步三份**：`shared/types.ts` → `preload/index.ts` → `renderer/src/global.d.ts`。`preload/index.ts:81` 已经导出了 `Api` 类型却没人用，`global.d.ts:16-53` 仍是手写副本（还额外手写了一个 `ScanResponse`）。加一个 IPC 要改三处，已经出现轻微漂移风险。建议 `global.d.ts` 改为 `import type { Api } from '../../preload'` 的映射类型。
5. **`Timeline.tsx` 17.9 KB 一个组件**，同时管加载、扫描、缩略图、元数据、下载、收藏、软删、分页、日期筛选、播放器档位、右键菜单。建议拆 `useMediaList` / `useThumbJobs` / `useMetaJobs` 等 hooks，是后续加功能前最值得做的一次重构。
6. **没有错误边界**：任何渲染异常 → 白屏，且没有重启入口。加一个 `ErrorBoundary` + "重新加载"按钮成本很低。
7. **可访问性**：工具栏的"全部/视频/照片""拍摄时间/大小"是 `<span onClick>`（`Timeline.tsx:361-369`），不可聚焦、无键盘可达；`DateFilter` 用了 `role="listbox"` 但子项没有 `aria-selected`。个人工具可以接受，但这是最容易被忽略的体验短板。
8. **无日志落盘**：只 `console.log`，打包版排查问题看不到。建议接 `electron-log`，顺手把 purge 的"删了什么"记一条审计（当前按用户要求没做审计，但日志是另一回事）。
9. `styles.css` 33 KB 单文件、`ContextMenu.tsx:20` 的 `MENU_H = 240` 硬编码、`MediaRow.fav: number` 用 0/1 —— 都是小问题，攒着一起清。
